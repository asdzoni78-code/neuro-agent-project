## 2. Пять принятых решений (основа v2.0)

1. **Сервер — делаем.** Рекомендация: **Supabase** (облачный Postgres + вход/роли + серверные функции). Ключи Claude и Telegram переезжают на сервер (в браузере их больше нет). Свой бэкенд писать почти не нужно.
2. **Смежные помещения — вручную.** Автоопределение невозможно без координат плана. Прораб при добавлении проёма ставит галочку «общий со смежным помещением» и выбирает какое; проём считается один раз.
3. **Порядок работ** — на ст.1 заполняется предварительно/примерно; **эталон берётся из ст.2** (по факту) и используется в расчётах высоты. Остальные поля ст.1 — обычные плановые значения (не «примерные»).
4. **«Сохранить» = «Зафиксировать готовую стадию».** Автосохранение в фоне остаётся. Пока стадия не заполнена — подсветка пропусков и переход дальше закрыт. Когда всё на месте — крупная кнопка «Сохранить», фиксация стадии (объединяется с уже готовым «замком» ст.1).
5. **Один продукт, два режима с ролями.** Вместо пароля в браузере (небезопасно) — настоящий вход через сервер. Роль «прораб» → только экраны ввода; роль «аудитор/Максим» → сравнение, отчёты, деньги.

## 3. Роли и режимы

| Роль | Устройство | Видит | Может |
|---|---|---|---|
| **Прораб** | Телефон | Помещения, Замер ст.1, Замер ст.2 | Вводить и фиксировать замеры. **НЕ видит** разницу, перерасход, деньги, отчёты |
| **Аудитор / Максим** | Ноутбук/телефон | Всё, включая «Итоги ст.1», «Сравнение», отчёты | Контроль, порог, справочник, «Сформировать отчёт» |

Режим определяется ролью учётной записи на сервере (не переключателем в UI).

        │  Supabase    │              │  Edge Function (сервер) │
        │  Auth+роли   │              │  прячет ключи:          │

- **Ключи (`ANTHROPIC_API_KEY`, `TG_BOT_TOKEN`) — только на сервере.** `config.js` в браузере для секретов больше не используется.
- **Хранение:** данные объекта живут в Postgres (переживают время, устройство, человека). localStorage — кэш/черновик и офлайн.
- **Миграция v1.0 → v2.0:** одноразовый импорт существующего `zamery_v1` из localStorage в базу при первом входе.

> Выбор именно Supabase — рекомендация, финально подтверждается в начале Ф12.

## 5. Модель данных v2.0

Ключевое изменение: **откосы больше не отдельный список — они принадлежат проёму, а проём принадлежит стене.** Проём может быть общим для двух помещений.

> **Реализация (Ф7):** проёмы хранятся ПОД стеной — `room.stage1.walls[key].openings[]`
> (стена известна по ключу A/B/V/G, отдельное поле `wall` не нужно). Размеры проёма
> ст.1/ст.2 лежат внутри самого проёма (`s1`/`s2`) — один список, не дублируется по
> стадиям (это устраняет баг «дверь исчезла на ст.2»). Ниже — логическая схема.

```jsonc
{
  "object":   { "id": "uuid", "name": "ул. Воровского 5, кв.12", "settings": { "overrunThresholdPct": 5 } },
  "materials": [ /* как в v1.0: id, name, norm, price, budget */ ],
  "floors": [{
    "id": "uuid", "name": "Этаж 1",
    "rooms": [{
      "id": "uuid", "name": "Кухня",
      "source": "manual | project",          // п.18: помечаем, откуда размеры
      "locked1": false, "locked2": false,     // п.4/8: зафиксированы ли стадии
      "workOrder": "screed_first|plaster_first|unknown",  // эталон из ст.2 (п.3)

      "stage1": { /* предварительно/план */ },
      "stage2": { /* факт */ },

      // Замер каждой стадии:
      //   height, length, width
      //   floor:   { materialId, thickness }   // ст.1 план, ст.2 факт (Δвысот)
      //   walls:   { A|B|V|G: { materialId, thickness } }  // материал редактируем и на ст.2 (п.12)
      //   columns: [ { id, sideA, sideB, height, materialId, thickness } ]  // п.6, авто-периметр (п.11)

      "openings": [{
        "id": "uuid",
        "type": "window | door | window_balcony | other",   // п.10 добавлен window_balcony
        "wall": "A|B|V|G",                                   // п.4/7: у каждого проёма указана стена
        "materialId": "plaster_g",                           // п.7: материал откоса
        "depth": 250,                                        // глубина плоскости откоса, мм
        "shared": { "roomId": "uuid|null", "countedHere": true },  // п.2: общий проём, считать один раз
        // размеры проёма по стадиям (для площади стены И для толщины откоса):
        "s1": { "w": 1200, "h": 1400, "doorW": 0, "doorH": 0 },   // doorW/H только для window_balcony
        "s2": { "w": 1180, "h": 1385, "doorW": 0, "doorH": 0 }
        // perimeter откоса — НЕ хранится, считается из размеров (п.11)
      }]
    }]
  }]
}
```

Все размеры — в мм. Материал стены/пола/колонны/откоса — своё поле, может отличаться между ст.1 (план) и ст.2 (факт) (п.12).

## 6. Формулы v2.0 (изменения и добавления)

Базовые формулы v1.0 сохраняются. Ниже — новое/уточнённое.

### 6.1. Авто-периметр откоса (п.11) — считается, не вводится
```
window / other:  perimeter = w + 2·h            (верх + 2 боковых, низ — подоконник)
door:            perimeter = w + 2·h            (верх + 2 боковых)
window_balcony:  perimeter = (w + doorW) + 2·doorH   (п.10: ширина окна+двери + высота двери×2)
```
Площадь откоса: `area = perimeter × depth / 1e6`.

### 6.2. Толщина откоса из разницы проёма (п.7, распространяется и на двери)
```
t_боковые = (w_s1 − w_s2) / 2      // проём сузился с двух сторон
t_верх    =  h_s1 − h_s2           // верхний откос
t_факт    = среднее доступных оценок; нет замеров ст.2 → t_факт = t_план
```
`расход = area × (t/10) × norm / 1000`. План — из ст.1, факт — из ст.2. Δ = план − факт.

### 6.3. Колонна двухстадийная (п.6) — ⚠️ требует подтверждения геометрии
```
perimeter = 2·(sideA + sideB)      // авто из сечения (п.11)
высота    = с учётом порядка работ (эталон ст.2):
              screed_first → height − толщина стяжки (или замер от чернового пола)
              иначе        → height
area      = perimeter × высота / 1e6
t_план    = ввод ст.1;  t_факт = из разницы сечения ст.1/ст.2 (формулу утвердить)
```
> **Открытый вопрос к заказчику:** как именно мерить фактическую толщину штукатурки на колонне — по приросту периметра между стадиями? Геометрия сечения неоднозначна, зафиксируем формулу перед кодом Ф9.

### 6.4. Площадь стены нетто — вычет проёмов (без изменений по сути)
`net = gross − Σ(проём.w × проём.h)`, где для `window_balcony` вычитается `w·h + doorW·doorH`. Общий проём (`shared.countedHere=false`) в расход откоса не идёт, но из площади стены вычитается в обоих помещениях (дырка есть в обеих стенах).

## 7. Экраны v2.0

### 7.1. Навигация (п.3) — 5 разделов
`Помещения · Замер 1 стадии · Итоги замеров 1 стадии · Замер 2 стадии · Сравнение`
На мобайле — компактная нижняя панель (иконки), возможно с группировкой, т.к. 5 пунктов.
Прораб видит только: `Помещения · Замер 1 стадии · Замер 2 стадии`.

### 7.2. Замер 1 стадии
Ввод: общие размеры; **порядок работ (предварительно)**; пол (материал + план.толщина); потолок — заглушка; стены А/Б/В/Г с толщинами; **проёмы** (окно/дверь/окно-с-балконной-дверью/другое — с указанием стены, размерами, материалом); колонны (сечение, высота, материал, план.толщина). Откосы **внутри проёмов**, отдельного списка нет (п.5). Периметры считаются авто (п.11).

### 7.3. Итоги замеров 1 стадии (п.4) — только просмотр
Свод по одной стадии: общие размеры; порядок работ; пол (материал+толщина); потолок-заглушка; стены А–Г с толщинами; проёмы окна (с указанием стены, все размеры) и двери (с указанием стены, все размеры); колонны.

### 7.4. Замер 2 стадии
Ввод факта. **Материал можно менять (п.12).** Порядок работ здесь — эталон. Рядом с каждой фактической толщиной (стены/пол/откосы/колонны) — **плановая из ст.1, разница и цветная метка** 🟢/🟡/🔴 (п.13). Авто-толщина откосов/колонн из разницы размеров.

### 7.5. Валидация и «Сохранить» (п.8)
Незаполненные обязательные поля ст.1 и ст.2 — подсветка заметным цветом + список пропусков. Крупная кнопка **«Сохранить / Зафиксировать стадию»** показывается только когда всё заполнено; фиксация «замораживает» стадию (объединено с замком из v1-доработок).

### 7.6. Сравнение (п.14, 15, 16)
- **Новая таблица (п.14):** строки — помещения, столбцы — результат по пол/стены/откосы/колонны с цветными метками; все параметры помещения, для точечного поиска проблемы.
- **Итоги (п.16):** тонны — «итого по каждому материалу» отдельно; **итого по объекту — только в рублях** (тонны разных материалов не складываем).
- **Баг (п.15):** штукатурка ЦПС показывала недорасход вместо перерасхода — разобрать `calcWall`/данные, исправить, покрыть тестом.

## 8. Обработка ошибок (v2.0, с сервером)

**Принцип v1.0 сохраняется:** пользователь видит только понятный русский текст; техника — в `console.error` (`logDev`) и в логах сервера. Таблицы ошибок LLM (4.1) и Telegram (4.2) из v1.0 остаются в силе, но вызовы Claude/Telegram теперь идут через серверную функцию, которая возвращает клиенту код ошибки, а клиент показывает русское сообщение.

Добавляются серверные/сессионные ошибки:

| Сценарий | Сообщение пользователю (RU) | Лог | Действие |
|---|---|---|---|
| Нет связи с сервером | «Нет связи с сервером. Проверьте интернет и попробуйте ещё раз.» | `[SRV] network` | «Повторить» |
| Сессия истекла / не авторизован | «Сессия закончилась. Войдите заново.» | `[AUTH] 401` | экран входа |
| Нет прав (прораб → раздел аудитора) | «Раздел доступен только аудитору.» | `[AUTH] 403` | скрыть раздел |
| Ошибка сохранения на сервере | «Не удалось сохранить. Данные остались на устройстве, попробуйте позже.» | `[SRV] save` | автоповтор + локальный кэш |

Резервный AI-отчёт по цифрам (`buildFallbackReport`) при любой ошибке LLM — остаётся.
